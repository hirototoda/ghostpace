# 0020. テストは Mac 全体の順番待ちで回し、UI テストの全件は TestFlight に送る前に回す
## 背景
いくつものチャットが、別々の作業場所とシミュレーターで同時に開発している。それぞれが PR のたびに UI テストを全件（約25件・単独で約10分）回すと、シミュレーターが同時に何台も動いて CPU が埋まり、Mac 全体が重くなる。実際、重なったときは同じテストに1.7倍の時間がかかっていた（17件で340秒 → 15件で570秒）。
## 決定
- テストは `scripts/test.sh` だけで回す。ビルドとテストを合わせて、同時に走るのは Mac 全体で2つまで。3つ目からは順番を待つ
- 2つ目は、メモリに余裕があるとき（macOS の判定が「通常」のとき）だけ使う
- UI テストは6件ずつの塊に分けて順番に並ぶ。1つのチャットが長く占有せず、各チャットの塊が交互に流れる
- `xcodebuild test` と XcodeBuildMCP の `test_sim` は Claude Code のフックで止める（実機で本物の時間を待つ確認だけ例外）
- PR では、ユニットテスト全件と、触った画面の UI テストだけを回す
- UI テストの全件は、`scripts/testflight.sh` が TestFlight に送る前に main で回す。失敗したら送らない
## 理由
- 分割しても全体の仕事量は減らない。重さを決めるのは「同時に何台動くか」なので、その上限を決める
- 2つは、この Mac（8コア・16GB）で重くなりすぎず、待ちも長くなりにくい数
- 測ってみると、先に足りなくなるのは CPU よりメモリだった。シミュレーターは1台で200を超える処理を動かし、テスト1本でもメモリの圧縮に CPU を使っていた。そのため2つ目はメモリに余裕があるときだけにした
- UI テストの全件の役目は「触っていない画面が壊れていないか」を見つけること。iPhone に届く前に1回通せば、オーナーの手元に壊れたものは届かない。ユニットテスト（433件・約10秒）は毎回全件回す
## 影響・トレードオフ
- 触っていない画面を壊した PR は、マージしたあと TestFlight に送る段階で見つかる。そのときは直す PR を出してから送り直す（ADR-0010 の自動マージの条件は変えない）
- 混んでいるとテストの結果が出るまで待つ。Claude はテストをバックグラウンドで回し、待つあいだ別の作業を進める
- TestFlight に送るのに、前より20〜40分長くかかる（Mac の混み具合による）。急ぐときは `--skip-tests` で飛ばせる
- フックは、main を取り込んだ作業場所で、チャットを開き直したときから効く
