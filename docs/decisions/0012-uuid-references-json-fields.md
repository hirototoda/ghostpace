# 0012. 保存データは UUID で参照し、版番号つきのスキーマで始める
## 背景
段階1a で記録の保存を始める（[recording-spec.md](../plan/recording-spec.md)）。記録を失わないこと（NFR-02）と、段階4の同期（ADR-0002）を両立させたい。
## 決定
- SwiftData のエンティティ同士は UUID で参照し、`@Relationship` は使わない
- 一意制約（`@Attribute(.unique)`）は付けない。重複は保存する側で防ぎ、読むときは決定的に1つ選ぶ
- 一時停止の区間と計画のスナップショットは JSON（Data）で1項目に保存する
- 最初から版番号つき（VersionedSchema の第1版＋MigrationPlan）で始める。形を変えるときは第2版を足す
- 保存に失敗したら変更を取り消し、「保存できませんでした」を出す（画面と保存内容をずらさない）
## 理由
- 関連の削除ルールで記録が連鎖して消える事故を避ける。スナップショットや同期で ID をそのまま運べる
- 一意制約は同期（段階4）で制約になりやすい
- Codable の配列を SwiftData にそのまま保存する方法は OS の版による挙動の差が報告されており、JSON の方が確実。読めない JSON でも記録そのものは読める
- 最初から版番号を持っていれば、あとで形を変えても第1版のデータを読み替えられる
## 影響・トレードオフ
- 関連をたどる処理（カテゴリ名の解決など）は Repository で手で書く。件数が少ないうちは問題にならない
- JSON の中身は SwiftData の検索条件に使えない（一時停止の回数で検索するなどは、読み出してから数える）
